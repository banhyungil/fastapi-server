# 이미지 압축 포맷 비교

## 주요 포맷

| 포맷 | 압축 방식 | 투명도 | 용도 |
|------|-----------|--------|------|
| JPEG | 손실 (DCT 기반) | X | 사진, 썸네일 |
| PNG | 무손실 (DEFLATE) | O | UI, 스크린샷, 투명 필요 시 |
| WebP | 손실/무손실 선택 | O | 웹 전반 (JPEG/PNG 대체) |
| AVIF | 손실/무손실 (AV1) | O | 차세대 웹 (최고 압축률) |
| TIFF | 무손실/손실 선택 | O | 의료·인쇄 등 고품질 보관 |
| BMP | 무압축 | O | 원시 데이터 (용량 큼) |

---

## JPEG Quality 파라미터

JPEG는 **DCT(이산 코사인 변환)** 후 양자화 단계에서 고주파 성분을 버려 압축한다. Quality(Q) 값이 양자화 테이블의 강도를 결정한다.

### OpenCV 사용법

```python
# Q=80으로 JPEG 인코딩
success, encoded = cv2.imencode(".jpg", image, [cv2.IMWRITE_JPEG_QUALITY, 80])
```

### Quality 값 범위 (0~100)

| Q 값 | 파일 크기 (상대) | 화질 | 용도 |
|-------|-----------------|------|------|
| 100 | 1x (기준) | 거의 무손실 | 원본 보관 |
| 95 | ~0.5x | 매우 좋음 | 고품질 출력 |
| **80** | ~0.2x | **육안 구분 불가** | **썸네일, 웹 일반** |
| 60 | ~0.1x | 약간 열화 | 저용량 필요 시 |
| 30 이하 | ~0.05x | 블록 아티팩트 심함 | 비권장 |

> **Q=80**은 품질과 용량의 최적 균형점. 150px 썸네일 기준 3~5KB 수준.

### Quality에 따른 실제 변화

- **Q=95→80**: 용량 60~70% 감소, 화질 차이 거의 없음
- **Q=80→60**: 용량 50% 추가 감소, 확대 시 블록 노이즈 감지
- **Q=60 이하**: 텍스트·경계선에서 아티팩트 뚜렷

## PNG vs JPEG 비교

| 항목 | PNG | JPEG Q=80 |
|------|-----|-----------|
| 압축 방식 | 무손실 | 손실 |
| 인코딩 속도 | 느림 | **2~3배 빠름** |
| 150px 썸네일 크기 | 20~50KB | **3~5KB** |
| 투명도 지원 | O | X |
| 적합 용도 | 원본 보존, 투명 배경 | 썸네일, 웹 표시 |

> 현재 프로젝트에서는 썸네일을 **PNG → JPEG Q=80 base64**로 전환하여 디스크 I/O 제거 + 용량 절감을 달성함.

## WebP (대안 포맷)

Google이 2010년에 개발한 웹 이미지 포맷. **Web** + **P**(icture)의 합성어로, VP8 비디오 코덱의 키프레임 압축 기술을 정지 이미지에 적용한 것이 기원.

- JPEG 대비 **25~35% 추가 용량 절감** (동일 화질 기준)
- 손실/무손실 모두 지원
- 투명도 지원 (PNG 대체 가능)
- 애니메이션 지원 (GIF 대체 가능)
- 모든 모던 브라우저 지원 (IE 미지원)

```python
# OpenCV WebP 인코딩
cv2.imencode(".webp", image, [cv2.IMWRITE_WEBP_QUALITY, 80])

# pyvips DZI 타일을 WebP로 생성
vips_image.dzsave(output_path, suffix=".webp[Q=80]", tile_size=256)
```

### JPEG vs WebP Tradeoff

| 항목 | JPEG | WebP |
|------|------|------|
| 용량 (동일 화질) | 1x (기준) | **0.65~0.75x (25~35% 절감)** |
| 인코딩 속도 | **빠름 (기준)** | 2~5배 느림 (압축 알고리즘 복잡) |
| 디코딩 속도 | **빠름** | 약간 느림 (브라우저 체감 차이 미미) |
| 호환성 | 모든 환경 | IE, 구형 이미지 뷰어, 일부 편집 도구 미지원 |
| 생태계 | Photoshop 등 네이티브 지원 | 전통 툴 지원 부족 |
| 최대 해상도 | 65535px | **16383px 제한** |
| 투명도 | X | O |

### 현재 프로젝트 기준 판단

- **썸네일 (base64)**: 150px 소형 이미지라 인코딩 속도 차이 미미. WebP 전환 시 네트워크 전송량 추가 절감 가능
- **DZI 타일**: 타일 수가 수백~수천 개이므로 **인코딩 속도 저하가 누적**됨. 용량 절감 vs 생성 시간 증가 트레이드오프 고려 필요

> 핵심 트레이드오프는 **인코딩 속도**. 이미지 수가 적으면 WebP가 유리하고, 대량 타일 생성처럼 인코딩이 반복되면 JPEG이 처리량에서 유리하다.

## base64 Data URL 방식

썸네일을 디스크에 저장하지 않고 base64 문자열로 직접 반환하는 방식.

```python
import base64

success, encoded = cv2.imencode(".jpg", thumbnail, [cv2.IMWRITE_JPEG_QUALITY, 80])
b64 = base64.b64encode(encoded.tobytes()).decode()
data_url = f"data:image/jpeg;base64,{b64}"
```

### 장점
- 디스크 I/O 완전 제거
- 캐시 파일 관리 불필요
- API 응답 하나로 이미지 전달 완료

### 단점
- base64 인코딩으로 원본 대비 **~33% 용량 증가** (네트워크 전송량)
- 클라이언트 메모리에 문자열로 유지 (노드 수 많으면 메모리 주의)
- 브라우저 캐싱 불가 (매 요청마다 전송)

### 적합 조건
- 이미지가 작을 때 (썸네일, 150px 이하)
- 실시간 생성·폐기되는 임시 이미지
- 별도 정적 파일 서버 없이 API만으로 서비스할 때
