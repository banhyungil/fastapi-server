# Database 개념 정리

## PK 전략: UUID vs Sequence

### Sequence (SERIAL / BIGSERIAL)

- DB가 자동 증가하는 정수를 생성
- 장점:
  - 인덱스 크기가 작고 정렬 효율이 좋음 (8바이트 vs UUID 16바이트)
  - 삽입 순서대로 정렬되어 B-tree 인덱스 성능 우수
  - 사람이 읽기 쉬움 (`/files/42`)
- 단점:
  - URL에 노출 시 예측 가능 → 다른 리소스 ID 추측 가능 (IDOR 취약점)
  - 클라이언트에서 사전 생성 불가 (INSERT 후에야 ID를 알 수 있음)
  - 분산 환경에서 충돌 가능 (서버마다 별도 시퀀스 관리 필요)

### UUID (v4)

- 128비트 랜덤 값, 충돌 확률 무시 가능
- 장점:
  - 예측 불가능 → URL 노출에 안전
  - 클라이언트에서 INSERT 전에 미리 생성 가능 → 관련 테이블 참조를 동시에 구성 가능
  - 분산 환경에서 충돌 없음 (서버 간 조율 불필요)
- 단점:
  - 인덱스 크기가 큼 (16바이트)
  - 랜덤 값이라 B-tree 삽입 시 페이지 분할 빈발 → INSERT 성능 저하
  - 사람이 읽기 어려움

### UUIDv7 (시간 기반)

- 앞부분에 타임스탬프가 포함된 UUID
- UUID의 보안/분산 장점 + Sequence의 정렬 성능 장점을 결합
- PostgreSQL 17+에서 `gen_random_uuid()` 대신 사용 가능

### IDOR (Insecure Direct Object Reference)

- API에서 리소스를 ID로 직접 참조할 때, 권한 검사 없이 접근을 허용하는 취약점
- 예: `/files/42` → `/files/43`으로 URL을 바꿔 다른 사용자의 파일에 접근 시도
- Sequence PK는 연속된 정수라 다음/이전 ID를 쉽게 추측 가능 → 공격 용이
- UUID PK는 랜덤이라 추측이 사실상 불가능 → 추가 방어층 역할
- **근본적인 방어는 서버 측 권한 검사** (요청자가 해당 리소스의 소유자인지 확인)
- UUID는 권한 검사를 대체하는 것이 아니라 보완하는 것

### 선택 기준

| 기준 | Sequence | UUID |
|------|----------|------|
| 소규모/로컬 전용 | 적합 | 과할 수 있음 |
| API 외부 노출 | 별도 보안 필요 | 자체로 안전 |
| 분산/멀티서버 | 조율 필요 | 바로 사용 가능 |
| INSERT 성능 중시 | 우수 | UUIDv7로 보완 가능 |
| 클라이언트 ID 사전생성 | 불가 | 가능 |
